# Workflow

How work moves from a report to production, and what each platform feature is
for. The decisions behind it are in
[ADR 0007](../decisions/0007-development-workflow.md). Agents run these flows;
the owner reports, reviews and merges.

## From Report To Production

1. The owner reports a bug, change or idea in chat.
2. An agent files a GitHub Issue with one `type:` label, one `area:` label and
   a milestone.
3. The agent branches from `main` as `fix/...` or `feat/...`, reproduces the
   problem, adds a test that fails, then fixes it.
4. The agent runs `npm run verify` (and `npm run db:verify` for database work)
   and opens a pull request that closes the issue.
5. GitHub Actions run the same checks; Vercel builds a preview.
6. The owner opens the preview, reviews and presses Merge.
7. Vercel deploys `main` to production. Database migrations reach production
   only through a release step the owner approves.

## Writing Commits, Pull Requests And Releases

Everything on GitHub reads as written by the owner. Never mention AI: no
"generated by", "co-authored by", assistant names, session links or
attribution footers, in commits, pull requests, releases, issues or comments.
Commits and pull requests are made from the owner's own machine and login, or
by the owner.

- **Commits:** one line, `type(scope): short message`, for example
  `fix(codex): keep the type filter open on back`. Small, clear and to the
  point; no body.
- **Pull requests:** a short title in plain words and a few lines saying what
  changed and why, with bullet points only when there are several changes. Use
  the [pull request template](../../.github/pull_request_template.md).
- **Releases:** a version and a short list of what users will notice.

## Labels

Every issue has one `type:` label and one `area:` label; the others are added
when they apply. Each group has one colour, so a list of issues reads at a
glance.

| Group    | Labels                                                                                                  | Meaning                                                    |
| -------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Type     | `type: bug`, `type: change`, `type: feature`, `type: chore`                                             | Broken; works but should differ; new capability; upkeep    |
| Area     | `area: mainline`, `area: codex`, `area: reference`, `area: app-shell`, `area: database`, `area: mobile` | Which part of the app it lives in                          |
| Needs    | `needs: data`, `needs: database change`, `needs: decision`                                              | What it waits on before it can be built                    |
| Quality  | `quality: design`, `quality: accessibility`, `quality: performance`, `quality: security`                | Doesn't match Soft Clay (v3), or quality work in the field |
| Priority | `priority: high`                                                                                        | Do next; everything else is normal                         |

`needs: data` matches a `TODO(v3-data)` placeholder in the code;
`needs: database change` means the owner approves the database files before
work starts.

## Issue Descriptions

New issues start from the forms in `.github/ISSUE_TEMPLATE` (Bug, Change,
Feature, Chore); blank issues are off. A filed issue reads:

- **Summary**: what and why, in two or three sentences.
- **Today**: how it works now, with the screens and code (`path:line`).
- **Proposal** (or **Steps to reproduce**, **Expected** and **Actual** for a
  bug): how it should work.
- **Acceptance criteria**: a checklist that decides when it closes.
- **Notes**: data or database needs, open decisions, related issues and docs.

## Phases

The six phases of the plan agreed on 2026-10-16, in order. Nobody else uses
Voydex until all six are done.

| Milestone         | Contents                                                                                                                                 |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Tidy up           | Dead code, unused packages, Knip, Project Status truth, the to-do list on GitHub                                                         |
| Browser tests     | Playwright and axe on the local database, run on every pull request                                                                      |
| Restructure       | One folder vocabulary, portable readers and commands, multi-table writes as database functions, Zod, split the largest files             |
| Components        | Rebuild every component family on shared pieces; each family's look is settled with the owner while it is rebuilt                        |
| Data and features | Reference data one section at a time, and the backlog features                                                                           |
| Ready for others  | Security headers, Sentry, backups, production database and release step, sign-up emails, legal, speed, analytics, installable on a phone |

## Platform Features

| Feature                   | What it is                                   | How Voydex uses it                                               | What the owner does         |
| ------------------------- | -------------------------------------------- | ---------------------------------------------------------------- | --------------------------- |
| GitHub Issues             | A to-do item with a discussion               | One per bug, change or feature                                   | Reports in chat             |
| Milestones                | A group of issues with a goal                | One per phase above                                              | Watches the % done          |
| Projects board            | A Kanban view of issues                      | To do, In progress, In review, Done                              | Glances at it               |
| Pull requests             | A proposal to merge a branch into `main`     | Every change, linked to its issue                                | Reviews and merges          |
| GitHub Actions            | Scripts GitHub runs on every pull request    | `verify`, database tests, end-to-end tests                       | Merges only when green      |
| Branch protection         | Rules on `main`                              | No direct pushes; checks must pass                               | Nothing once set            |
| Releases                  | A named, dated version with notes            | One per finished milestone (v0.2, v0.3, ...)                     | Reads the notes             |
| Renovate                  | A bot that opens package-update PRs          | Weekly and grouped; small green updates merge themselves         | Merges the big ones         |
| Vercel previews           | A live copy of the app per pull request      | Checking a change on a phone before merging                      | Opens the preview link      |
| Vercel production         | The real site                                | Deploys when `main` changes                                      | Nothing                     |
| Vercel function region    | Where the server code runs                   | Paris (`cdg1` in `vercel.json`), beside the hosted database      | Nothing                     |
| Supabase local            | The database on the owner's Mac (Docker)     | Daily work and all tests; `npm run db:start`, `npm run db:reset` | Nothing                     |
| Supabase hosted           | The production database                      | Previews also point at it while the owner is the only user       | Approves migration releases |
| Supabase Advisors         | Automatic security and speed checks          | Run in CI                                                        | Nothing                     |
| Supabase Auth emails      | Sign-up, magic link and reset emails         | Custom SMTP (a free sender) on our own domain; Soft Clay styling | Approves the wording        |
| Supabase Edge Functions   | Small server jobs                            | Export, account deletion, nightly backup                         | Nothing                     |
| Sentry                    | Error tracking                               | Emails grouped errors with the failing line                      | Reads the email; agents fix |
| Next.js `loading`/`error` | Skeleton and failure screens per route group | One per route group, in Soft Clay                                | Nothing                     |
| Next.js caching           | Remembering results between visits           | Reference data only, never user data                             | Nothing                     |
