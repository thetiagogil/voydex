# Database Decisions

This document records rationale for non-obvious database choices. It does not
repeat the current table inventory or implementation status.

## Schemas By Responsibility

Reference facts, tracking definitions, gameplay state, planning state, derived
views, and internal helpers change for different reasons and have different
security models. They therefore use separate schemas. Frontend modules remain a
separate concern.

## Identifiers

- Stable curated reference rows use deterministic integer IDs.
- User-owned roots use UUIDs generated by the database.
- High-volume relationship/progress rows use natural composite keys when those
  keys express identity.
- UUID values remain compatible across UUIDv4 and UUIDv7-capable Postgres
  versions; the schema does not expose version-specific assumptions to the app.

## Historical Identity

Current team rows are intentionally mutable because a Pokémon evolves or
changes form. Meaningful events copy species/form identity into event refs and
optional snapshots. This preserves biography and collection history without
turning normal correction edits into an audit log.

## Sparse Progress

Milestone, collectible, and Pokedex progress store positive or meaningful user
state. Missing rows express defaults. This avoids pre-creating large per-play
matrices and makes completion rules explicit in queries and views.

## Plays And Plans

Plans exist before plays and remain after play creation. A play has one focused
linked plan so progress semantics remain understandable. Planned targets are
not copied into the active roster until the user actually obtains them.

## Derived Collection And Stats

Collection, reuse history, dashboard summaries, completion, and stats are read
models over authoritative user state. They are not manually maintained primary
tables. Caching is a later performance decision, not a new source of truth.

## Rules And Personalization

Global preferences provide defaults. Structured predefined rules can influence
validation and analysis; custom descriptive rules document user intent even
when the app cannot enforce them. Tags are global user-owned entities with typed
joins rather than duplicated text on feature rows.

## Reference Depth

Reference data is deliberately Pokémon-relevant rather than encyclopedic. The
item catalogue, availability, and tracking definitions exist to support the
play, planning, and history workflows. Full locations, encounters, story gates,
and platform-specific rerelease differences remain future data domains until a
product slice needs them.

## Security And Read Models

Client-readable facts are read-only; user-owned state is protected by grants
and RLS; multi-table functions run as security invoker. App-facing views use
`security_invoker = true` so they inherit underlying RLS. See
[Security And Indexing](./security.md) for operational rules.
